# SimpleMark — Product contract

* **Status:** Current product authority

* **Date:** 2026-08-04

* **Decision:** Rendered document first; editing is an escape hatch; every change is a block-level
  transaction regardless of author; agent participation and collaboration are expansion capabilities

## The job

AI writes Markdown. A human needs to read it, judge it, trust it, and occasionally correct it.

SimpleMark is the display surface for that work:

> **Open Markdown generated by any AI and see a beautiful, living technical document—without
> surrendering the file.**

The user is not primarily authoring Markdown and is not trying to operate an AI system. Claude,
Codex, another agent, or an existing tool has already produced the artifact. The user wants to get
out of the coding environment, see the result as a real document, and keep reading while the agent
updates it.

Another useful expression of the promise is:

> **Your agent writes the Markdown. SimpleMark turns it into a document.**

This is closer to Preview for AI documents than to another Markdown editor, IDE, knowledge base, or
agent workspace.

## The complete first experience

1. Open any `.md` file directly. Do not import it into a library, create a vault, or choose a
   workspace.
2. Show the rendered ==document== ==immediately==. The document—not a file picker, editor, chat, session,
   or dashboard—is the product surface.
3. Make prose, typography, spacing, tables, code, Mermaid, SVG, math, and other technical material
   look exceptional in one continuous canvas.
4. Watch the file and update the rendered document cleanly when an AI or another tool changes it.
   Preserve reading position and avoid flashing, jumping, or stealing focus.
5. Let the human click into a sentence or rendered block for a small correction. Editing is
   available where the correction is needed; raw Markdown is not the default view.
6. Preserve the source. An untouched save is byte-identical, and changing one block does not
   normalize unrelated content.
7. Close the app and leave an ordinary Markdown file in the same place.

If this experience is not excellent, agent transactions, live collaboration, comments, history,
and multi-client authority do not compensate for it.

## Who this is for

The primary user:

* asks AI to create plans, research, specifications, reports, runbooks, notes, and technical
  explanations as Markdown;

* dislikes reading long documents in a terminal, source editor, chat transcript, or IDE preview;

* wants technical material rendered correctly without setting up plugins;

* treats documents as living artifacts that an agent may revise over time;

* wants to make an occasional correction without becoming a Markdown author; and

* wants the original local file to remain portable, inspectable, and theirs.

The first market is not “everyone who writes Markdown.” It is people who increasingly **consume AI
output as Markdown** and need a better place to read and judge it.

## The category difference

The inspected products are solving a different job. Their assumed user wants to **operate AI work**:
choose models, manage sessions, supervise edits, review diffs, comment, collaborate, inspect history,
manage files, and recover mistakes. Markdown is the convenient substrate underneath that control
system.

That explains their product shapes:

| Product        | The job it is built around                                   | Why its interface grows                                                                    |
| -------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| **MerMark**    | Put AI chat and file tools inside the editor                 | Chat, providers, file operations, execution state, and editing all need controls           |
| **NeverWrite** | Build an IDE for supervising AI knowledge work               | Sessions, artifacts, attribution, review, navigation, and state become permanent surfaces  |
| **CollabMD**   | Build a self-hosted collaborative workspace using Markdown   | Rooms, users, presence, comments, history, recovery, and administration become the product |
| **Mindle**     | Let humans annotate and direct documents agents are changing | Anchors, events, instructions, status, and agent activity must remain visible              |

Those needs are real. They are not the SimpleMark wedge.

SimpleMark assumes:

> **AI composes. The human consumes, judges, and directs.**

The competitors largely assume:

> **The human composes or supervises inside an AI-enabled work environment.**

The distinction is not “fewer features.” It is a different primary object. Their primary object is
the workspace, session, or control system. SimpleMark's primary object is the rendered document.

## Why the category becomes a cockpit

The common interfaces are a predictable result of their product assumptions:

1. **They expose the system instead of the artifact.** The UI is organized around workspaces,
   sessions, providers, files, participants, runs, and history rather than around the page.
2. **They surface implementation nouns.** Model, context, MCP, snapshot, tool call, branch, diff,
   thread, and presence may be necessary internally, but every visible noun taxes the reader.
3. **True rendered editing is hard.** It is easier to show Markdown beside a preview than to map a
   beautiful structured canvas back to byte-preserved source. The easy implementation leaks syntax,
   modes, and layout movement into the experience.
4. **AI features are easy to demonstrate.** A model picker, chat panel, and sparkling action produce
   obvious screenshots. Typography, reading continuity, exact source preservation, and a view that
   stays calm during external updates require more disciplined proof.
5. **The builders are often their own advanced users.** Developer workflows naturally import file
   trees, command palettes, panes, inspectors, and configuration surfaces from IDEs.
6. **Scope becomes the attempt at defensibility.** Search, folders, exports, comments, cloud sync,
   teams, and AI actions accumulate until the document is surrounded by product machinery.

SimpleMark should not make those mechanisms visible merely because it implements them.

## Product rules

### 1. The document opens first

Opening SimpleMark with a file goes straight to the rendered document. No empty editor, vault
creation, workspace chooser, provider setup, model picker, agent inventory, session list, or review
dashboard may stand between the file and the page.

### 2. Rendered is the default and persistent state

Markdown punctuation is storage syntax, not the user interface. Headings look like headings, tables
look like tables, code is readable, and diagrams are diagrams. Source appears only for the exact
thing the user chooses to correct, then disappears again.

### 3. Reading quality is a feature, not polish

Typography, line length, spacing, hierarchy, contrast, code treatment, diagram framing, table
behavior, selection, and scroll stability are acceptance criteria. “It renders” is insufficient.
The goal is a document a person wants to keep open all day.

### 3a. Deliberate app choices survive reopen

SimpleMark remembers stable choices a person makes: pane arrangement, reader typography, whole-page
magnification, visible reader tools, note and folder sorting, preview density, filters, column widths,
the active collection, and native window placement. Reopening the app should resume the working
environment, not reconstruct factory defaults. This state is local presentation state and never
enters Markdown.

Momentary interaction state still ends normally: open menus and popovers, hover, caret and selection,
drag-in-progress, unfinished find text, loading indicators, and errors are not preferences. Trackpad
pinch magnifies the complete app canvas like a browser; Command-plus and Command-minus change reader
text size; Command-zero restores both to actual size.

### 4. External change is ordinary

An AI updating the file is the normal workflow, not a conflict edge case. SimpleMark watches the
same file, refreshes only what changed, preserves reading position, and makes the update legible
without turning every revision into a review ceremony.

Watching a file as it changes is a **desktop capability**. It requires a real filesystem and
directory notification, which mobile does not provide and cloud propagation does not deliver
promptly. On a phone or tablet, SimpleMark reads documents that have already arrived. We say that
plainly rather than implying the desktop experience travels.

### 4a. The update is the same no matter who made it

**Settled, and not reopened by later work.** Every change to a document — a human correcting a
sentence, an AI revising a section, another client in a live session, or an external tool rewriting
the file on disk — arrives as the same thing: a **named, attributed, block-level transaction** on
the structured ProseMirror document.

There is no second mechanism and no privileged author. A file landing from disk is imported as a
transaction like any other; it is simply the lossiest source, because it delivers bytes and makes us
re-derive the blocks that moved. Everything downstream — rendering only what changed, preserving
reading position, byte-identical re-emission of untouched blocks, attribution, revert, and telling
the reader what happened — reads from that one representation.

This is the property the product is built on: **the page updates beautifully and identically no
matter who is editing.** Any proposal that introduces a separate path for a particular kind of
author is wrong by construction.

### 5. Editing is a small correction path

The human can fix a sentence, table cell, diagram source, or formatting mistake directly. That does
not turn the default surface into an authoring cockpit. Broader requests can be handed back to the
agent outside SimpleMark or through a later quiet affordance.

### 6. The file is never surrendered

SimpleMark opens the original local file rather than importing a copy into proprietary storage.
Untouched bytes stay untouched. Edited content saves as portable Markdown. No account or hosted
workspace is required to retain the document.

### 7. Machinery stays latent

File watching, source maps, atomic writes, parser errors, renderer isolation, run fencing, document
authority, attribution, and recovery may all exist. They appear only when the user needs to act on
them. Implemented capability does not earn permanent screen space.

### 8. Sync is the user's cloud, not ours

SimpleMark never operates a sync service. Documents move between a person's devices through the
cloud drive they already pay for — iCloud Drive, Dropbox, Google Drive, OneDrive — and every one of
them is treated identically as a folder on disk. **No provider is privileged and no provider-specific
code is written**, including iCloud: a customer with a Windows machine and an iPhone is served by
Dropbox or OneDrive and would be stranded by an Apple-first path.

Two consequences follow. Cloud-backed files may be placeholders whose bytes are not local, so
"exists but not here yet" is an ordinary state and directory listing never reads content. And a
provider that produces a conflicted copy has produced something we must show rather than merge —
the one visible surface sync is permitted to add. Rule 6 makes that rare: a reading session writes
nothing, so it cannot conflict.

### 9. Web and native are the same product

Neither shell is a preview of the other and neither has its own document model. The web client opens
and saves real local files today, and in a live document it sends and receives the same block-level
transactions as every other client, per rule 4a.

What the web client never grows is a **second way to reach storage**: no per-provider accounts,
connection settings, OAuth pickers, or hosted drive browsers. Where files are concerned, the browser
reads and writes what the person points it at, exactly as the native shell does.

## What the first product is not

The first compelling release is not:

* a Markdown authoring environment;

* an AI chat client;

* an agent control plane;

* a project, folder, vault, or knowledge workspace;

* a collaboration suite;

* a review queue or diff dashboard;

* a model or provider manager;

* a session-history browser; or

* a second filesystem.

These are explicit non-goals for the primary experience even if narrow versions later exist behind
an action.

## Sequencing

The order of proof is now:

1. **Beautiful rendered document.** Prove that representative AI-generated Markdown looks
   exceptional as a real document.
2. **Trustworthy local file.** Open any file, preserve untouched source, save atomically, and never
   import or rewrite the user's artifact unexpectedly.
3. **Living external updates.** Let Codex, Claude, or another tool change the file while SimpleMark
   remains a calm, current reading surface.
4. **Small direct corrections.** Reveal editing only at the selected content and return immediately
   to the rendered state.
5. **Broader renderer coverage.** Mermaid, SVG, math, tables, code, and the most common technical
   artifacts must feel native to the page.
6. **Optional agent participation.** Test scoped transactions, attribution, redirect, Stop, and
   revert only after the reader product is worth installing without them.
7. **Optional collaboration.** Test additional humans, clients, presence, and multi-client authority
   only after real use demonstrates a need that local files and external updates do not satisfy.

[`ADR-0005`](decisions/0005-rendered-document-before-agent-participation.md) records this sequencing
decision. It changes what ships first; it does not discard the existing `DocumentSession`, fencing,
MCP, or collaboration designs. Those remain prepared expansion architecture, not the install reason.

## The first demo

The canonical product demonstration is one continuous shot:

1. An agent writes `plan.md` in a terminal or coding agent.
2. SimpleMark opens the same file directly and already shows a polished document.
3. Prose, tables, code, Mermaid, SVG, and math render inline without setup.
4. The agent changes the file; the rendered page updates without losing the reader's place.
5. The human clicks one sentence, corrects it, and the page returns to its rendered state.
6. The file is opened in a plain-text tool to prove it is still ordinary Markdown and untouched
   content has not been reformatted.

Do not lead the first demo with chat, model selection, inviting an agent, a collaboration room,
presence, comments, activity, history, or settings. Those demonstrate machinery instead of value.

This is a rule about **what leads**, not a ban on the capability. Anchored notes
([`ADR-0007`](decisions/0007-annotation-before-participation.md)) are the one item on that list that
ships early, and they obey the rule rather than escape it: nothing appears until a person highlights
a passage and asks for it, and the rail is gone again once nothing is unresolved. Demonstrate them
where they are actually useful — reading a document with someone and capturing what they said —
never as a feature tour of a comment system.

## Language to use

Lead with:

* **The beautiful living document for AI work.**

* **Your agent writes the Markdown. SimpleMark turns it into a document.**

* **Open Markdown generated by any AI and see a beautiful, living technical document.**

* **Always rendered. Always your file.**

* **Read AI output outside the coding environment.**

Support with concrete proof:

* Opens local `.md` files directly.

* Updates while the agent works.

* Renders technical content inline.

* Lets you correct the document without living in Markdown source.

* Preserves untouched source byte for byte.

* Requires no IDE, vault, account, provider setup, or workspace.

Avoid leading with:

* Markdown editor;

* AI workspace;

* multiplayer notebook;

* human-agent collaboration;

* MCP;

* `DocumentSession`;

* CRDT or Yjs;

* model/provider choice; or

* universal paste.

Those phrases either describe implementation, point at the wrong job, or place SimpleMark inside a
crowded cockpit category.

## Product acceptance questions

A release is moving toward this product only if the answers are yes:

1. Can someone open an AI-generated `.md` file and reach a beautiful page immediately?
2. Is raw Markdown absent until the user deliberately edits one thing?
3. Do the representative technical documents look better than an IDE or GitHub preview?
4. Can an external agent update the file without disrupting the reader?
5. Can the human correct a small error without entering a separate editor mode?
6. Does an untouched file remain byte-identical?
7. Does a local edit leave unrelated source untouched?
8. Can the user understand the product without learning any AI, collaboration, or storage concept?
9. Is the document still an ordinary local file after SimpleMark closes?
10. Would the product remain worth installing if every collaboration feature were removed?

If the answer to question 10 is no, the product has drifted back toward the category it is meant to
escape.
