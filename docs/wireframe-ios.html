SimpleMark · design wireframe

The iPhone: three panes become a stack, one rail becomes a sheet

The desktop's Library, Notes and Document panes cannot sit side by side at 390pt. They become a navigation stack. The Library rail becomes a sheet, which satisfies the no-permanent-rail rule for free. Nothing collaborative gains a surface it does not already have.

Companion to wireframe.html, wireframe-bear.html and wireframe-collaboration.html. Governed by DESIGN.md §6 & §10.1, NATIVE-WORKSPACE.md, BEAR-INSPIRED-EDITING.md, and ADR-0001/0003/0006. Revised after the first working iOS build — §4 records what that build proved.

The storage decision this wireframe assumes. SimpleMark owns one iCloud Drive folder, published to the Files app. Bring-your-own-cloud — pointing the app at an existing Dropbox, Drive or iCloud folder — remains the goal and is not drawn here as if it worked. iOS hands an app a security-scoped bookmark rather than a folder, and third-party File Providers may refuse to enumerate in the background. The open question in DESIGN.md §12 stays open; §5 below records what would have to be true.

New in this revision

This screen did not exist before, and it is the one the shipped build is stuck on. The iOS app currently boots to a welcome placeholder whose row is not a real file, so tapping it does nothing and there is no way forward.

Two ways out, both honest: write a note, or bring one in. Neither pretends a folder was chosen — the folder is a fact of the platform, so the screen states where notes live rather than asking.

Changed

“Edit” is gone. In iOS convention it means multi-select and delete, and iOS has no Trash for an app to move a document into. Keeping it would advertise a capability the platform refuses.

The duplicate scope control is gone. The title chevron and the old footer button opened the same sheet. The footer now carries sync state instead — the one thing a person cannot otherwise know.

Changed — the storage decision

SimpleMark's own iCloud folder is now the first row, because it is where notes actually are. Folders are folders inside it.

“Add Folder from Files” is demoted to a disabled row with its reason written on it. It previously promised iCloud, Dropbox, OneDrive “or any Files provider”. Bring-your-own-cloud stays the goal; the row says why it is not here yet instead of implying it works.

DESIGN.md §12 open question · ADR-0006 provider-neutral materialization
Changed

Back now reads Library rather than a dead end, so the stack is complete in both directions: Library → Folder → Document.

The old “Folder access” footer button is gone with the arbitrary-folder capability it belonged to.

Changed

A save state now sits under the title. The desktop titlebar has always shown “Saved · 14:22”; the phone dropped it. With iCloud in the loop and D7 fidelity at stake, a person has to know their correction landed.

Back is labelled with the folder it returns to, which is what makes this a stack rather than a hidden pane.

New

Correcting had no frame at all. “Correct” was drawn as a button with no state behind it and no way back.

Cancel and Done bracket the edit; the styles bar rides above the keyboard rather than becoming a permanent ribbon. That is Bear's restraint, which BEAR-INSPIRED-EDITING.md already adopts: the document stays dominant and the tools appear when the cursor needs them.

This is where the macOS menu bar went, and it was previously an unspecified “⋯”.

Two rows are deliberately disabled with their reasons visible: Delete, because iOS has no Trash — the shipped build already returns that as a named limitation rather than failing silently — and Print, because iOS printing is UIPrintInteractionController, not a webview call.

Unchanged

Already right. The anchored note is a sheet over the passage, carries its anchor text, and says out loud that it is stored outside the .md — which is what keeps D7 true.

New — and required

ADR-0006 requires this screen and it did not exist. A conflicted copy is a new file and never silently enters the stream; overlapping unsaved state demands an explicit keep / import / merge decision.

The banner is the general error surface too — “changed on disk by another program”, “could not open file”. In the shipped build those messages are written into an element the phone stylesheet hides, so failures are invisible. A message nobody can see is not a message.

3What the first working iOS build proved

These are not predictions. Each was observed on device during the first successful tauri ios build, and each constrains the design above.

An absolute path is not a stable identity on iOS. The app's data container UUID changes on reinstall — observed moving across three UUIDs in one session — and will change again on update or restore. WorkspaceCatalogPort currently documents the native handle as “the canonical absolute path”. On iOS that is false, and any persisted handle must be stored relative to the container and resolved at load time. Consequence: every screen above stores note and folder handles as container-relative paths, never absolute ones.
ObservedWhat the design does about it
Container UUID changes between installsHandles are container-relative; nothing persists an absolute path.
No Trash exists for an app documentDelete is a disabled row in ⋯ with its reason, and points at Files.
No file watcher — notify has no iOS backendConflict screen is required, because changes arrive without warning. A watcher is NSFilePresenter work, not a port change.
Errors are written into an element the phone hidesThe banner in §1 is the error surface, above the document and impossible to miss.
Document picker reaches the app's own folder“Bring a file in from Files…” on first run is proven to work.
File associations carry over from tauri.conf.jsonMarkdown opened elsewhere can hand off to SimpleMark.

4What would have to be true for bring-your-own-cloud

The disabled row in the Library sheet is a placeholder for this list, not a decision against it.

RequirementStatus
Handles survive as security-scoped bookmarks, resolved and re-scoped on every accessPort contract change; not started
A third-party File Provider will enumerate a folder's direct children on demandUnverified — the open question in DESIGN.md §12
External writes are observable through NSFilePresenter outside the app's own containerUnverified
A materialization group can be paired across Mac and phone without inferring it from a pathDesigned in ADR-0006; unbuilt

Until the two unverified rows are answered on a real device with a real provider, the honest product is one folder the application owns. That is a smaller promise, and it is one iOS actually keeps.
